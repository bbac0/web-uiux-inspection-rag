# 확인 3: 1,181쪽 가이드라인에서 청크가 732개뿐인 이유

작성 2026-11-19. API 호출 없음(임베딩 호출 없음). PDF 를 색인 코드와 같은 방식으로 다시 읽고 나눠 보았고,
실험에 쓴 DB(`services/chroma_db/chroma.sqlite3`)는 읽기 전용으로 열었다.

방법: `services/indexer.py` 와 같은 `PyPDFLoader(pdf).load()` →
`RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)` → 빈 청크 제외.
글자 수는 쪽별 `page_content.strip()` 길이. 로컬 pypdf 6.16.2.

## 1. 결론

- **글자가 거의 없는 쪽 때문이 아니다.** `gov_guide.pdf` 는 1,181쪽 모두 글자가 추출되고(0자 쪽 0개, 50자 미만 10쪽),
  같은 규칙으로 나누면 **1,197청크**가 나온다.
- **실험 DB 가 `gov_guide.pdf` 의 앞부분(1~736쪽)만 담고 있다.** DB 의 gov_guide 청크 732개는 1~736쪽 중 721쪽에서
  나왔고, 그 721쪽의 쪽별 청크 수는 다시 나눈 결과와 모두 같다(불일치 0쪽). 빠진 것은
  - 737~1,181쪽 445쪽 전체(다시 나누면 450청크),
  - 중간의 707~711쪽, 722~731쪽 15쪽(15청크)이다.
- `gov_check.pdf` 는 273쪽 전부, 288청크로 다시 나눈 결과와 같다.
- DB 메타데이터의 PDF 정보(쪽수 1,181, 생성·수정 날짜, 생성기)는 현재 `data/gov_guide.pdf` 와 같다. 다른 판의 PDF 가 아니다.

- gov_guide 는 쪽당 글자가 적어(중앙값 311자) 대부분의 쪽이 1청크(1,000자 이하)가 된다. 그래서 쪽수에 비해 청크가 적지만,
  다시 나누면 1,197청크로 쪽수(1,181)와 비슷하다. 732개라는 수는 이것으로 설명되지 않는다.

## 3. 다시 나눈 결과와 실험 DB 비교

| 항목 | gov_guide.pdf | gov_check.pdf |
|---|---|---|
| 다시 나눈 청크 | 1,197 | 288 |
| 실험 DB 청크 | 732 | 288 |
| DB 에 청크가 있는 쪽 | 721 (1~736쪽 중) | 273 |
| DB 에 없는 쪽 | 707~711, 722~731, 737~1,181 (460쪽) | 없음 |
| DB 청크가 있는 쪽에서 쪽별 청크 수 불일치 | 0쪽 | 0쪽 |

출처: `services/chroma_db/chroma.sqlite3` (embedding_metadata 의 source, page; 읽기 전용), 재추출 결과

- DB 의 청크 합계 1,020 은 색인 코드의 배치 크기 10의 102배다. 색인 코드는 배치마다 `add_documents` 를 부르고,
  예외가 나면 메시지를 출력하고 10초 기다린 뒤 **그 배치를 다시 시도하지 않고** 다음 배치로 넘어간다
  (`services/indexer.py` 57~72행). 중간에 빠진 15쪽은 이렇게 건너뛴 배치일 수 있다.
- 737쪽 이후가 통째로 없는 이유는 저장소에 색인 실행 기록이 없어 확인할 수 없다(실행 중단 또는 연속 실패로 추정만 가능).
  DB 의 source 경로는 이 컴퓨터가 아닌 다른 컴퓨터의 경로여서, 색인은 다른 컴퓨터에서 만든 것으로 보인다.
- 영향: 모든 RAG 조건(고정 질의, 페이지별 질의)은 gov_guide 737쪽 이후 내용을 검색할 수 없었다. 관련 조항 제공
  조건(E3, E9)의 청크는 모두 gov_check.pdf 에 있어 이 누락과 무관하다. 실험 DB 는 동결 대상이므로 고치지 않았다.
