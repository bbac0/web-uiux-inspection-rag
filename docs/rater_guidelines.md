# 평가자 지침서 (초안)

웹 UI/UX 자동 검수 시스템이 보고한 이슈를 사람이 판정하기 위한 지침이다. 두 명의 평가자가 서로 상의하지 않고 각자 판정한다.
평가 시트(`eval_sheet.csv`)에는 페이지가 어떤 결함을 주입받았는지, 어떤 실험 조건에서 나온 이슈인지, 자동 채점기가 어떻게
분류했는지가 들어 있지 않다. 이런 정보를 찾아보지 말고, 시트에 있는 이슈 설명, 제안, 페이지 스크린샷, 페이지 HTML 만 보고 판정한다.

## 1. 한 행에서 판정하는 것

각 행은 시스템이 보고한 이슈 한 건이다. 다음 세 가지를 판정한다.

1. **분류** (6개 중 하나): 이 이슈가 주로 지적하는 문제가 무엇인가.
2. **코드에 존재하는가** (`exists_in_code`): 이 이슈가 지적한 결함이 페이지의 HTML/CSS 코드에 실제로 있는가.
3. **화면에서 보이는가** (`visible_on_screen`): 이 이슈가 지적한 결함을 렌더링된 화면(스크린샷)에서 눈으로 확인할 수 있는가.

4. **로그인 링크 레이블 지적** (`login_link_label_concern`): 이 이슈가 로그인 링크(또는 로그인 버튼) 레이블의 **문구 또는 의미 명확성**을 지적하는가.

2와 3은 각각 `예` / `아니오` / `판단 불가` 중 하나로 답한다. 분류가 "해당 없음"이어도 2와 3은 이슈 설명이 지적한 내용 기준으로 답한다.
4는 `예` / `아니오` 로 답한다. 4는 6분류와 따로 판단한다(6분류에서 무엇을 골랐든 4를 따로 답한다).

## 2. 분류 6개

| 분류 | 이렇게 지적하면 이 분류 | 이 분류가 아닌 것 |
|---|---|---|
| 명도 대비 부족 | 글자색과 배경색의 대비가 낮아 읽기 어렵다 | 색상이 브랜드 가이드와 다르다(대비 언급 없이) |
| 모바일 레이아웃 깨짐 | 고정 폭, 강제 가로 스크롤 등으로 화면 폭에 따라 레이아웃이 깨지거나 요소가 넘친다 | viewport meta 태그가 없다는 지적만 있는 경우 → 해당 없음 |
| 버튼 영역 잘림 | 버튼이 CSS(높이, 글자 크기, overflow 등) 때문에 잘리거나 거의 안 보이거나 누를 수 없다 | 버튼 디자인이 표준 스타일과 다르다 |
| 표준 용어 위반 | 링크, 버튼, 제목 같은 UI 레이블의 용어가 비표준이거나 모호해 표준 용어로 바꿔야 한다 | 오탈자, 문장이 길다 |
| 중복 ID | 같은 `id` 값이 문서에서 두 번 이상 쓰였다 | WAI-ARIA 일반 권고, 레이블-입력 연결 문제 |
| 해당 없음 | 위 다섯 가지에 해당하지 않는 모든 지적 (autocomplete, 제목 계층, 콘텐츠 부족, 스타일 일관성, 일반 접근성 권고 등) | |

한 이슈가 여러 문제를 함께 말하면 **설명의 중심이 되는 문제** 하나를 고른다. 판단이 어려우면 비고에 이유를 적는다.

## 3. "코드에 존재하는가"와 "화면에서 보이는가"의 차이

두 질문은 서로 다르다. 코드에는 있지만 화면에서는 보이지 않는 결함이 있고, 이 테스트베드에는 그런 경우가 실제로 있다.

- **코드에 존재하는가:** HTML/CSS 원문을 읽었을 때 그 결함의 원인이 되는 코드가 있는지를 본다. 화면에 어떻게 나오는지는 따지지 않는다.
- **화면에서 보이는가:** 스크린샷(데스크톱 1280x800 기준)만 보고, 일반 사용자가 그 문제를 눈으로 알아챌 수 있는지를 본다. 코드는 보지 않는다.

### 예시 1: 버튼이 없는 페이지의 버튼 CSS 규칙

페이지 `<head>` 에 `button, .btn { height: 2px !important; font-size: 0px !important; ... }` 규칙이 있지만,
본문에는 `<button>` 요소나 `.btn` 클래스를 가진 요소가 하나도 없다. 이슈가 "버튼이 잘려 클릭할 수 없다"고 말한다면:

| 질문 | 답 | 이유 |
|---|---|---|
| 분류 | 버튼 영역 잘림 | 설명이 버튼 잘림을 지적한다 |
| 코드에 존재하는가 | 예 | 버튼을 찌그러뜨리는 CSS 규칙이 코드에 있다 |
| 화면에서 보이는가 | 아니오 | 적용될 버튼이 없어서 화면에는 잘린 버튼이 없다 |

### 예시 2: 화면에 보이지 않는 중복 ID

`<body>` 바로 아래에 `<div id="main-banner"></div><div id="main-banner"></div>` 처럼 내용이 없는 요소 두 개가 같은 id 를 쓴다.
이슈가 "id 가 중복되었다"고 말한다면:

| 질문 | 답 | 이유 |
|---|---|---|
| 분류 | 중복 ID | |
| 코드에 존재하는가 | 예 | 같은 id 가 두 번 쓰였다 |
| 화면에서 보이는가 | 아니오 | 중복 ID 는 마크업 문제라 화면에 드러나지 않는다 (빈 요소라 면적도 없다) |

### 예시 3: 둘 다 예

페이지 전체 글자가 아주 연한 회색(#e5e5e5)이고 배경이 흰색이다. 이슈가 "명도 대비가 부족하다"고 말한다면
코드에 존재하는가 `예`, 화면에서 보이는가 `예` 이다.

### 예시 4: 둘 다 아니오

이슈가 "로그인 링크의 용어가 비표준이다"라고 말하지만 페이지 코드와 화면 어디에도 로그인 링크나 비표준 용어가 없다면
코드에 존재하는가 `아니오`, 화면에서 보이는가 `아니오` 이다.

### 판단 불가

스크린샷이 잘렸거나 HTML 이 일부만 제공되어 확인할 수 없을 때만 고른다. 애매하다는 이유만으로는 고르지 말고, 가장 가까운 답을 고른 뒤 비고에 적는다.

## 3-1. "로그인 링크 레이블 지적" 열 (`login_link_label_concern`)

정의: **이슈가 로그인 링크 레이블의 문구 또는 의미 명확성을 지적하는가.**
로그인 화면으로 가는 링크·버튼에 쓰인 글자(레이블)가 무엇을 하는지 알기 어렵다, 표준적이지 않다, 다른 말로 바꾸는 게 낫다는 식의 지적이면 `예`.
이슈 설명에 그 레이블 문구가 단순히 **언급만** 되고 지적의 대상이 다른 것(위치, 마크업, 크기, 색 등)이면 `아니오`.

| 이슈 설명 예 | 답 | 이유 |
|---|---|---|
| "'접속하기' 링크는 목적이 불명확하다. '로그인'으로 바꾸는 것이 좋다." | 예 | 로그인 링크 레이블의 의미 명확성을 지적 |
| "링크 텍스트 '접속하기'가 연결될 페이지의 목적(로그인)을 명확하게 전달하지 못한다." | 예 | 레이블 문구가 목적을 전달하지 못한다는 지적 |
| "'접속하기' 링크가 `<nav>` 요소로 감싸져 있지 않다." | 아니오 | 레이블은 언급만 되고 지적 대상은 마크업 구조 |
| "색상 대비가 낮아 글자를 읽기 어렵다." | 아니오 | 로그인 링크 레이블과 무관 |

## 4. 진행 방법

1. 시트의 순서는 무작위다. 순서대로 판정하고, 같은 페이지 이슈를 모아 보려고 정렬하지 않는다.
2. 한 행에 2~3분 이내를 목표로 한다. 판단에 오래 걸린 행은 비고에 표시한다.
3. 두 평가자는 판정이 끝날 때까지 서로의 시트를 보지 않는다. 불일치는 분석 단계에서 따로 목록으로 만든다.
4. 평가 전 연습: 시트와 별도로 제공하는 연습 문항 10개로 기준을 맞춘다(연습 문항은 분석에 넣지 않는다).

(초안 작성: 2026-11-12. 5단계에서 시트 형식이 확정되면 열 이름을 맞춰 갱신한다.)
